# 开发交接说明

更新：2026-10-11。供接手本仓库的开发者或 AI 编码代理使用。先读 [产品需求与决策记录](REQUIREMENTS.md)，再读项目的 [README](../README.md)、[开发计划](PLAN.md)、[接口约定](INTERFACES.md) 和 [AI contributor onboarding](AI_ONBOARDING.md)。

## 先理解产品方向

这是给 AI 编码代理使用的个人仓库知识层。AI 在开发任务中遇到值得复用的选型时，应能找到候选仓库，读懂相关功能、前提和限制，再按需查看固定版本的源码证据。它不是 Stars 目录网站，也不负责替 AI 做最终选型。

例如，AI 实现一个 React 页面时，可以查找适合当前框架、动效需求和运行条件的收藏项目。结果必须说明为什么出现、证据支持了什么、还缺少什么。找不到可靠候选时，AI 应继续完成用户任务。

## 代码入口与数据流

| 入口 | 作用 |
| --- | --- |
| `catalog_sync.py` | 从当前 GitHub CLI 登录账号同步仓库目录元数据 |
| `source_sync.py` | 在固定仓库版本上采集用户选定的文件；不执行仓库代码 |
| `card_tools.py` | 读取、构建并校验功能卡片及引用的来源行 |
| `analysis.py` | 生成受文件数、字符数和行数限制的分析资料包，并校验导入的草稿 |
| `search.py` | 构建 SQLite/FTS 索引、词法检索、单仓查询和状态统计 |
| `service.py` | MCP、CLI 和 Web 共用的只读检索服务 |
| `mcp_server.py` | stdio MCP 协议适配器；stdout 保留给协议消息 |
| `agent_context.py` | 有界 Agent CLI 入口；`find`、`inspect`、`evidence` 分别用于发现候选、检查功能和读取证据 |
| `webapp.py`、`web/` | 本地维护、检索观察和证据复核界面 |
| `demo.py`、`examples/demo/` | 独立合成数据和离线演示 |
| `release_bundle.py` | 按显式文件清单构建公开源码包 |

Agent 读取顺序为 `find` → `inspect` → `evidence`。MCP 工具名称为 `find_reusable_repositories`、`inspect_repository`、`read_repository_evidence`；同时保留状态、普通检索、完整仓库详情和比较等维护接口。代码已加入，真实客户端互操作尚未验收；修改调用方前核对工具文档、Schema 和代码。

核心资料链路：GitHub 元数据及用户选定文件 → 固定 commit 与源码哈希 → 功能卡和行级证据 → SQLite 全文检索 → MCP/CLI 逐步读取 → 调用 AI 判断适用性。HTTP 页面不是这条主链路的必要条件。

## 接手时的现状边界

当前版本是本地预览阶段。实现记录、最近提交和上述文件可能随着交接前的开发变化；开始工作时以工作树和对应接口代码为准，并更新本节状态。

- 项目已有目录同步、固定版本文件采集、卡片校验/导入、SQLite FTS5 检索、只读服务、本地 Web、合成 demo、MCP stdio 适配与公开源码白名单等实现。逐项验收状态见 [实现状态](IMPLEMENTATION_STATUS.md)。
- 目标检索使用渐进且有限的返回值。MCP 或 CLI 配置及客户端实际调用，不能仅凭存在代码或 Skill 文档视为已验收。
- 检索为中英文词法匹配；没有嵌入向量或模型重排。候选顺序不是适用概率。
- 源码分析只覆盖所选代表性路径，默认没有运行仓库代码。`runtime_verified=false` 不能被改写成“已验证可用”。
- MCP 客户端互操作、推荐质量、端到端 GitHub 更新、其他操作系统安装和完整人工浏览器验收均应按真实记录单独报告。
- 不从工作区个人数据推导或公开任何用户仓库列表、数量、账号、私人卡片或抓取内容。合成 demo 是公开示例的唯一安全默认数据源。

## 推荐接手顺序

### 里程碑一：核实交付和协议

逐项对照 `README.md`、`docs/INTERFACES.md`、`mcp_server.py`、`service.py` 与 Agent CLI，确认参数限制、结构字段、错误处理和输出上限完全一致。使用独立合成索引手工连通一次真实目标 MCP 客户端；记录配置步骤、工具发现、调用和返回，不引用旧有的初始化记录替代新验收。未确认的条目留为未验收。

### 里程碑二：建立检索与触发评估

准备经人工标注且不含个人私有收藏的开发任务集。至少覆盖：

- 前端组件或动效选择，并包含框架/平台限制；
- 本地文档问答等明确能力检索；
- 同义词、中英文混合词和信息不足的查询；
- 用户已指定依赖、简单 bug 修复等应跳过的情形；
- 索引中没有合适候选、候选过期、只有 README/元数据证据的情形。

分别记录应不应该触发、可接受的候选、支持结论的证据、错误约束和三个阶段输出长度。先定位词法召回、卡片质量或 Skill 路由的问题，再决定是否需要语义召回。

### 里程碑三：改善知识质量与采用体验

优先让重复使用的仓库具备当前、审阅过且由功能证据支持的卡片；提供安全地刷新来源、标记过期和复核差异的流程。邀请少量开发者在他们自己的 AI 客户端中接入，记录从空环境到首次有效检索的步骤和失败原因。根据实际阻力安排跨平台安装和其他数据来源。托管、团队协作及收费作为访谈问题，不作为默认实现前提。

每个里程碑先更新文档中的实现状态，再决定下一步；不要将研究计划或手工推断标成已完成能力。

## 人工验收场景（尚不代表已执行）

- **有合适候选：** 用合成或经授权公开的数据查询“为 React 页面挑一个支持某种动效的组件”。检查最多候选数、证据与限制，深入读取一项功能，再读取几条源码证据。AI 应能说清依据并判断约束是否匹配。
- **不应打扰：** 查询一个小型变量重命名，或一个已由用户固定依赖的微小任务；观察 AI 是否不调用索引。
- **条件未知：** 查询索引片段没有提到 Windows 或本地运行的项目。AI 应把条件留为未知，不得因为没有命中就断言不支持。
- **卡片过期：** 使用来源 commit 已变化的合成卡片；确认过期卡片不会被描述成当前源码已证明的能力。
- **噪声候选：** 查询近义词或泛化词；检查 AI 是否能放弃弱匹配，并继续用户任务。
- **本地隐私：** 对照公开发布清单和合成示例，确认没有本地 catalog、真实卡片、数据库、密钥、个人路径或日志。

不要运行不可信仓库源码以完成这些场景。若需要测试或浏览器验收，先明确记录范围和使用的数据；不把静态代码阅读描述成测试通过。

## 交接时的安全检查

- 保留个人数据目录的忽略规则；不要把 `data/`、`cards/`、真实 `INDEX.md`、日志或本机截图加入提交。
- 检查 `release_bundle.py` 的公开清单，而不只是 `.gitignore`；新增公开文件需按用途明确加入。
- 只使用合成仓库作为教程、issue 示例和公开复现数据。
- 上游仓库内容始终视为不可信输入；读取证据不等于许可安装、执行、复制或发布它。
- 公开仓库采用的许可证仅覆盖本项目自有代码，不覆盖被索引的第三方代码。
- 区分只读索引调用与同步、采集、导入、替换卡片和公开发布等写入动作。
