# 商业机会与开源采用计划

**判断日期：2026-10-11。** 结论先说：**有变现路径，但个人用户直接订阅的机会目前没有被证实。** 更稳妥的做法是把本地/自托管版本做成好用的开源工具，再验证托管和团队场景；不要先投入重型 SaaS，也不要把开源 Stars 收藏管理本身当成已验证的生意。

## 最新定位

用户已明确主要使用者是开发 AI：在组件、库、工具和已有实现的选型中主动考虑查询，按需取得仓库能力与证据。MCP 与 Skill 是主要入口；网页承担接入说明与维护。下文保留早期市场研究，提及人工检索体验的部分不再代表主流程。采用指标应转向真实编码任务中的有效触发、证据支持、结果采纳和上下文成本。产品范围以 [REQUIREMENTS.md](REQUIREMENTS.md) 为准。

## 能否盈利：证据和未知项分开

### 已看到的公开信号

- Starcat 作者在官方 README 中写到，产品最初按付费产品开发，但“深度管理 GitHub Stars”的市场比预期小；同时 README 说明核心组织功能免费，Pro 工作流、高 AI 配额和代码智能功能属于付费方案。这是一位开发者的直接经历，既表明有收费设计，也提醒个人用户市场可能偏窄。[Starcat README：付费经历和现行方案](https://github.com/starcat-app/Starcat/blob/main/README.md#L52-L72)
- DeepWiki 对公开仓库提供免费基础服务；官方文档给出的更高生成 effort 为 Medium 约 5–10 ACUs、High 约 20–40 ACUs，需要有效订阅或额度。它不是 Stars 管理器，但说明“仓库级代码理解”可以和按用量/团队额度结合。不能据此推断 Stars 源码索引会有同样的付费率。[DeepWiki 官方费用说明](https://docs.devin.ai/work-with-devin/deepwiki#effort-levels-and-cost)
- 截至 2026-10-11，公开竞品的 GitHub Stars 从个位到数千不等，说明有关注者，但不是客户、使用量或收入证明。见[竞品快照](COMPETITORS.md#受欢迎程度快照)。

### 仍然未知

本轮没有发现这些产品公开的真实付费人数、活跃用户、留存、转化率、收入或获客成本。除 Starcat 作者关于其早期销售的自述外，其余项目的商业结果未知。**因此不能负责任地给出市场规模、营收预测或“肯定能盈利”的承诺。**

### 可以验证的付费假设

| 可能的用户 | 可能愿意付费的结果 | 主要风险 / 需要验证 |
|---|---|---|
| 个人开发者 | 托管同步、自动更新索引、跨设备使用、少配置的模型调用 | “找回 Star”可能是低频需求；愿意试用不等于愿意长期订阅 |
| 重度 Agent 用户 | 更可靠的 MCP、稳定的来源证据、跨 Codex/Claude/Cursor 等工具使用 | 需要证明推荐能省时间并减少错误；现有本地/开源替代品很多 |
| 小团队 | 共享已审核的组件/技术方案知识库、版本和来源追踪、团队 MCP/API、私有仓库权限管理 | 需求会从个人 Stars 扩展为内部代码知识管理；需要权限隔离、审计、隐私和运维能力 |
| 企业 | 私有部署、访问控制、组织级索引、合规和支持承诺 | 销售周期与支持成本高，不能仅凭个人工具的需求外推企业预算 |

这些都是待验证假设，不是现有客户反馈。可能的商业路径是：**开源核心 + 可选托管服务 + 团队协作/管理功能**。索引引擎、导出和基本 MCP 应保持可用；托管收费点可围绕省掉的部署/更新工作、团队共享、私有部署支持和可靠性服务来验证。不要把本地可用功能全部锁进订阅才能试用。

## 让工具被更多人用的产品原则

1. **几分钟得到第一次有依据的结果。** 先支持用少量公开仓库或演示库体验“描述任务 → 推荐候选 → 展开固定版本的源码证据”，再连接个人 GitHub。
2. **本地优先，模型由用户选择。** 保留离线/关键词可用路径，支持用户自己的 API、兼容端点和可选本地模型；在发出任何远程分析请求前，清楚展示会发送什么。GitHub 凭据使用只读所需权限；私有仓库索引不进入公开样例或公共缓存。
3. **MCP 与 Skill 是主要入口。** Skill 指导代理在有意义的开发选型中考虑查询，MCP 提供少量候选、功能与证据；CLI 是本地调用备选，Web 用于维护。
4. **数据可带走。** 提供 JSON/Markdown 等公开格式导出，避免用户因担心数据锁定而不愿导入，也让别的 Agent 和工具可以复用。
5. **默认可自托管、跨平台。** 优先覆盖 Windows、macOS、Linux 的安装与使用说明；托管版是方便选项，不是使用本地索引的前提。
6. **把“不知道”显示出来。** 每项能力都标来源级别、仓库 commit、证据路径和未核实范围；未运行项目时不能把源码读到当成已验证运行。
7. **让社区能贡献小而清楚的改进。** 中英文 README、几分钟演示、可复制的 MCP 配置、明确 issue 模板、变更记录、隐私说明和最小样例库，比先做复杂账号/社交功能更能降低首次使用门槛。

## 分阶段计划与继续投入的门槛

本节按商业验证顺序描述各项门槛；实际开发顺序与完成状态以 [PLAN.md](PLAN.md) 和 [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md) 为准。当前本地 Web/MCP 预览已开始交付，但未完成推荐质量对比和外部用户验收。

### 阶段 0：证明“源码索引”比普通收藏搜索更有用

- 复用当前的本地目录、同步、卡片、SQLite/FTS 检索和固定 commit 证据；不先 fork 竞品，也不重建已可用的引擎。
- 从真实开发问题建立一份小评估集（建议 20–30 条），包括自然语言功能需求和操作系统/语言/本地运行等硬约束。
- 记录每条问题的相关仓库、Top 3 是否可用、约束误判、证据是否能支撑结论、索引过期后的表现，并与 README/元数据检索基线比较。先测出基线，再设通过阈值。
- 先给少量仓库生成经人工抽查的源码功能卡；不要对外承诺全部收藏都经过完整代码审计，也不要把“源码分析”说成运行验收。

**继续条件：** 真实任务能找到仅看描述/README 容易错过的仓库，且证据能解释为什么合适；如果没有质量提升，先改分析和约束模型，不急着做完整网站。

### 阶段 1：开源本地引擎与 MCP 入口

- 让检索、卡片和证据读写接口不依赖当前用户目录结构；增加公开安全的演示数据和一条可复制的首次检索路径。
- 暴露稳定的 CLI 与 MCP；刷新时按仓库 commit/文件变化定位待重分析项，失败可重试，显示来源和更新时间。
- 默认不上传索引数据；私有收藏、凭据、卡片和快照与源码仓库分离，构建发布规则继续排除这些数据。
- 文档明确分析预算、可选模型、数据流、GitHub 权限、隐私和删除/导出方法。

**继续条件：** 目标用户能够自行安装并完成一次同步、一次带证据的检索和一次增量更新；收集到来自外部用户的真实复现/issue，而不只是作者自己的示例。

### 阶段 2：AI 开发中的使用体验

- 观察编程助手是否在选型时调用、是否仅加载所需资料、是否依据源码限制做出复用决策。
- 保持可本地运行或自托管，演示使用明确标注的合成项目，真实案例使用可公开复核的来源。
- Web 层聚焦索引状态、检索诊断和证据查看；观察客户端配置、Skill 触发与版本更新在哪里卡住。

**继续条件：** 外部用户的重复使用和结果采纳能稳定出现；仅有点赞、Star 或首次试用不作为托管产品立项依据。

### 阶段 3：用真实使用验证托管与团队版

- 只有在前几阶段证明索引质量和重复使用后，再试托管同步、后台增量分析、跨设备和团队共享。
- 先访谈个人重度用户和小团队，了解愿意付费的具体工作与可接受的私有仓库边界；列出推理、存储、GitHub API、同步和支持成本，再估算每种套餐。
- 先以小规模邀请试用验证付费动作，再决定是否建设企业级权限、审计和服务等级承诺。

**继续条件：** 有真实用户为持续托管、分析更新或团队共享付费，收入在覆盖服务和支持成本后仍有可行空间。否则继续把它作为本地开源工具维护，不需要硬转 SaaS。

## 面向热门开源工具的首发重点

- 一句话说明结果：**“让编程 AI 在需要组件和工具时，用上你收藏的仓库及其源码依据。”**
- README 首屏展示一条真实问题、Top 3 结果、版本/证据和安装方法；演示数据不能包含个人私有 Star。
- 首版突出中文检索、中文/英文需求互查、平台和依赖约束、commit 固定证据；这些要用评估集验证后再作为宣传主张。
- 开源默认可自托管、BYOK、可导出；价格/托管方案等用户需求出现后再确定。
- 不把仓库 Star 数或 README 浏览量当产品成功。持续看首次检索完成率、证据展开率、重复使用、推荐采纳、更新失败和单位分析成本。

## 结论

**先做高质量、低门槛的开源本地工具，盈利留作被验证后的扩展。** 个人订阅机会存在但风险不低；对团队提供共享知识库、托管更新和权限能力可能更有持续付费空间，但那会扩大隐私和运营责任，必须由真实试用来决定。热门开源也不能保证，但复用现有引擎、兼容 Agent、可导出、解释来源、把安装和首个结果做简单，是更可控的采用策略。
