# 开发计划

更新：2026-10-11。产品定位：给开发 AI 提供一层按需检索的个人仓库知识库，帮助它在合适的开发任务中发现可复用项目、理解关键功能与限制，并用固定版本源码证据支持选择。

## 要解决的问题

AI 开始实现功能时，通常不知道开发者已经收藏过哪些可能有用的仓库。收藏列表只能告诉它“有哪些仓库”，README 也常不足以说明组件如何接入、行为如何实现、平台前提是什么。让人再维护一份 Stars 浏览页，并不能解决 AI 缺少项目理解的问题。

本项目把仓库功能、适用场景、前提、限制、未知项与固定 commit 证据整理成可检索资料。开发 AI 在需要选择组件、动效库、工具、依赖或已有实现时查询，再按需读取少量功能与源码证据，最后由调用 AI 结合用户需求判断是否复用。索引只提供有依据的候选，不替 AI 决策，也不在服务端调用模型。

## 方案与边界

- **索引数据：** 用户选择的 Stars 元数据、固定版本文件快照和逐功能分析卡。
- **AI 接口：** MCP 提供 task search → feature inspection → pinned evidence 的渐进读取；本地 CLI 提供相同用途的有限输出备用入口。
- **触发方式：** Skill 描述何时应考虑查询，例如正在做前端并挑选可复用动效组件。它是代理路由指导，不是所有客户端都有的强制 hook；MCP 仍须由实际客户端配置。
- **网页：** 检查索引覆盖、过期状态、搜索表现与证据的维护界面，不把“浏览全部 Star”当主要流程。
- **质量边界：** 默认是中英文词法检索。可选的 embedding 融合（RRF）已实现，需用户自行配置提供方并运行 `search.py embed`；未配置时行为与纯词法一致。代表性源码分析不等于完整审计或运行验证；固定引用不自动证明解释正确。

- [x] 同步当前 GitHub CLI 登录账号，支持独立数据根目录并让可见性未知的数据默认留在本地。

## 阶段二：验证 Agent 何时查、结果是否有用

1. 建立 20–30 个真实开发任务，例如“为 React 页面找可复用的动画组件”“找本地文档问答实现”；标注应该触发、应该跳过以及可复用项目。
2. 对比 Skill 触发是否覆盖有选型价值的任务，是否在简单修复和用户固定方案时打扰工作流。
3. 记录候选中实际适用的比例、硬约束错误、证据支持度、检索上下文长度，以及 AI 是否最终采用该仓库。
4. 找出索引薄弱项后，再评估模型辅助分析：挑选关键文件 → 固定版本采集 → 生成草稿 → 引用校验 → 人工审阅 → 更新功能卡。记录成本和失败原因。
5. 根据对照结果决定是否进一步调优；向量召回（embedding 融合）已实现为可选层，需用标注任务集验证其是否真的改善口语化查询，不把检索分数包装成正确率。
6. 用 commit 变化使旧结论失效，优先对重复使用的公开仓库缓存；私有数据继续独立留存。

阶段目标是证明 AI 能在需要复用的任务里更快找到适用项目，同时少加载无关仓库、少给出无证据推荐。达不到时优先改进触发、卡片和检索，不扩成另一个 Stars 管理器。

## 阶段三：开源采用

- 邀请 5–10 位收藏较多的开发者，把自己的索引接入实际 AI 编码流程。
- 关注接入耗时、触发准确性、重复使用、上下文节省和推荐错误；让安装方式不依赖本项目作者的账号或数据。
- 准备公开仓库、独立合成演示、安装文档、问题模板与贡献入口。外部发布作为单独步骤。
- 公开包只包含代码和合成样例，不包含任何个人 Stars、卡片或源码快照；对外分享的案例需用户主动选择。

## 阶段四：商业验证

优先维持本地、完整的开源个人工作流。可以访谈团队是否愿意为共享组件知识库、私有索引托管、自动刷新或支持服务付费；目前没有需求或收入证据。先验证团队实际使用频率和愿付成本，再考虑托管、账号和计费。

## 执行约束

默认不调用付费模型、不运行第三方仓库、不把个人索引上传或发布。实际任务需要同步、安装、执行、验证或外部发布时，按任务范围安排。本次产品化工作附带 `tests/` 单元测试（`python -m pytest tests/`），覆盖索引构建与检索、固定快照采集；未覆盖 MCP 互操作、网页和推荐质量。开发状态、静态审阅、服务启动、浏览器验收、MCP 互操作和推荐质量评估分别报告。
