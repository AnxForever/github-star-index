# 产品需求与决策记录

状态：产品方向基线，2026-10-11。本文整理用户已明确表达的需求；标为“提议”的内容需要结合验证结果调整。

## 产品目标

为 AI 编码代理提供一层本地、可引用证据的仓库知识索引。当 AI 正在实现功能并需要决定“自己写还是复用已有项目”时，帮助它快速发现用户已经收藏或整理过的相关仓库，理解具体能力、接入条件和限制，再由 AI 结合当前任务决定是否采用。

索引要回答的是“哪些仓库可能解决眼前这个开发问题，依据是什么”，而不是“用户收藏过什么”。产品价值来自 AI 对仓库功能的深入了解和恰当复用，不来自再做一个 Stars 浏览器。

## 用户与使用时机

### 已确认的关键决策

| 需求演进 | 当前决定 |
| --- | --- |
| 收藏太多，AI 只看简介仍不了解项目 | 建立深入的功能卡、限制说明与源码证据索引 |
| 人工检索网页仍要用户主动查找 | 以开发 AI 为主要调用方，在真实开发的选型环节按需召回 |
| 前端任务需要现成组件和动效 | 将组件与实现复用作为首批验收场景 |
| 希望其他人也能使用，争取成为热门开源工具 | 公开代码、提供可移植 Skill 和合成演示，优先验证采用与效果 |
| 希望了解盈利机会 | 保留商业假设与竞品研究，收入能力尚未验证 |
| 准备交由其他开发者继续 | 维护需求基线、接口、当前限制与可执行的接手顺序 |

### 使用者与触发时机

- **主要使用者：** 编码 AI 代理；它在开发过程里调用索引。
- **直接受益者：** 希望 AI 复用自己的开源收藏、少从零重复造轮子的开发者。
- **维护者：** 开发者可以准备索引、补充或复核项目功能卡、更新来源快照；维护界面是辅助能力。
- **合适时机：** AI 正在选择前端组件或动效库、库和框架、开发工具，或准备从零实现一项较大的可复用能力。
- **不必触发：** 小型文案或样式修正、用户已经指定唯一依赖且无替代选择、与仓库复用无关的问题。索引 Skill 提供调用指导；具体触发仍由 AI 客户端决定。

## 核心工作流

以“给前端页面添加一套动效”为例：

1. AI 将当前任务、已知约束和少量同义检索词提交给索引。
2. 索引返回少量候选、为何命中、卡片状态、已知前提与限制，以及值得继续看的功能线索。
3. AI 只检查相关候选和具体功能，确认支持的框架、运行环境、许可证及其他任务约束。
4. AI 按需读取固定 commit 的短源码证据，判断描述是否真能支持当前方案。
5. AI 选择是否复用并继续完成用户任务；索引不代替 AI 决策，不在后台自行调用模型或执行仓库代码。

渐进读取接口：`find` 发现候选 → `inspect` 检查能力卡 → `evidence` 读取少量关键证据。MCP 是面向代理的首选接口；无法连接 MCP 时可由本地 CLI 提供同类工作流。Web 界面用于维护覆盖度、复核资料和排查检索，不作为核心推荐入口。

## 必须满足的产品要求

### 能力资料

- 对项目具体功能做有边界的总结，不能只改写 README 或仓库描述。
- 尽可能说明输入、行为、输出、接入方式、运行前提、平台限制、许可证、已知问题和未验证项。
- 功能判断应关联固定 commit 的文件、行号与短摘录；README 或相关背景片段不能冒充某功能的实现证据。
- 区分元数据、README、文档、代表性源码和实际运行验证。读了部分源码不能称为完整审计；引用行正确也不等于解释一定正确。
- 仓库版本变化后使旧资料显式过期，避免 AI 把过期卡片当作当前结论。

### AI 检索

- 检索面向当前任务和约束，默认只返回少量候选；不把全部索引或长篇源码塞进上下文。
- 支持同义词或补充词，帮助中英文开发任务匹配项目常见术语。
- 先发现，再读特定功能，最后按需读证据；各阶段都应有明确结果上限。
- 让 AI 看见候选为何出现、依据来自哪里、什么仍未知，以及下一步可读取哪些信息。
- 词法匹配结果不代表语义相关度或适用概率。未命中的条件是未知，不能据此断言仓库不支持。
- 检索结果不足时，AI 应说明证据缺口并自行继续工作，而不是为了凑推荐而推荐。

### 接入与维护

- 提供可在用户自己的 AI 编码环境中配置的 MCP 服务和适当的 Skill 路由说明；不得宣称未配置客户端也会自动调用。
- 索引可由用户自有仓库来源生成；当前优先支持用户经 GitHub CLI 授权后读取的 Stars。未来支持其他来源必须单独设计和验证。
- 用户能检查索引新鲜度、分析覆盖度、过期卡片和检索错误，并选择更新或复核资料。
- 提供不依赖模型、网络和个人真实数据的合成演示。

### 隐私、许可与安全

- 个人索引、私有仓库资料、抓取源码、卡片及生成数据库默认留在用户本地，不进入公开代码仓库、演示或日志。
- 对外公开范围必须采用确认公开的仓库白名单；可见性未知的数据默认排除。
- 不因检索到仓库就自动 clone、安装依赖、运行代码、上传内容或调用付费模型。
- 上游仓库内容是不可信参考资料，不能覆盖当前 AI 指令或授予执行权限。
- 项目代码许可不替代第三方仓库源码与文档自身的版权、许可证和使用条件。

## 明确不作为当前目标

- 面向人浏览、收藏、分类 Stars 的又一个网站。
- 自动替开发者选库、保证推荐正确，或把词法分数包装成匹配准确率。
- 对所有用户提示词强行检索，或承诺每种 AI 客户端都能自动唤起工具。
- 无审阅的全量自动分析、全仓库安全审计或运行时兼容认证。
- 默认把用户私有索引托管到云端、跨用户共享个人收藏，或通过用户数据训练服务。
- 在尚无用户访谈、实际使用和付费证据前，优先做订阅、账号、团队面板或商业宣传。

## 如何判断是否有效

以下为产品验收维度，不是已测得的结果：

1. **触发合适：** 有复用选型价值的任务会查询；小改动和已固定方案不会频繁打断。
2. **找到相关项目：** 在标注的真实开发任务里评估应有候选的召回、误报、遗漏和不相关结果，而非仅统计索引大小。
3. **理解有依据：** 推荐的关键能力能由功能级来源支持；硬性约束错误和把未知说成不支持的情况可单独统计。
4. **节省上下文：** 记录发现、详情、证据三阶段各自返回的仓库数、字符或 token 数，并与直接加载大量 README/Stars 比较。
5. **接入够轻：** 新用户能按文档建立自己的索引、连接一个 AI 客户端并完成一次端到端复用任务。
6. **维护有反馈：** 仓库版本变化能暴露过期资料，维护者能补充资料并解释修改依据。

建议先用约 20–30 个开发任务建立人工标注集，覆盖前端组件、动画、文档问答、开发工具等不同场景，同时包含应跳过的简单任务。比较触发、候选质量、证据充分度及上下文消耗。样本数和阈值属于待验证方案，不应作为产品已达成承诺。

## 公开采用与商业假设

首要目标是做成容易安装、能在常见 AI 编码流程里发挥作用的开源工具。采用情况应由实际接入耗时、重复使用、误触发、推荐错误、上下文长度和贡献者反馈判断。

**商业化仍是待验证假设。** 可在开源核心被真实使用后访谈团队，了解是否愿意为团队共享的代码库知识、私有索引托管、更新服务或支持付费。没有证据前，不为营收叙事牺牲本地优先、个人可用和透明可审阅的核心体验。

## 可讨论的后续方向

以下均非当前承诺：AI 辅助生成待审阅卡片、增量重分析、结构化兼容条件、向量召回或重排、其他代码收藏源、跨客户端安装向导、团队共享与托管。应由检索质量、接入反馈和安全边界的数据决定优先级。
